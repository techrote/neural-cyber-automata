# Original-operator CPU follow-up

The owner requested further project progress on 20 October. This T109 follow-up
adds an explicit `torch-operators-cpu/v1` deployment backend for the same fixed
evaluated BC1103 numeric policy. It leaves the
[original NumPy deployment no-go](2026-10-19-t109-deployment-no-go.md), all
original source/artifact records and every original arithmetic/trajectory
tolerance unchanged. There is no retraining, checkpoint selection, quantization,
new host source or morphology experiment.

## Why an additional backend

The retained NumPy result passed all 160 common-input comparisons but failed
both actual closed-loop trajectory comparisons. That audit did not establish a
unique cause. A separate read-only operator check reconstructed all 80 retained
Torch trajectory decisions from the immutable numeric weights with zero hidden,
value and continuous-action difference. It imported no learner module and made
no host request. This supports testing a runtime which retains the original
batch-one Torch operator path; it does not retrospectively qualify NumPy or
prove that the host is intrinsically deterministic.

The new wrapper binds the original numeric content and evaluated lineage,
explicit Torch CPU version/thread/arithmetic settings, operator graph and
runtime source closure. It retains `runtime_qualified: false` at conversion;
qualification belongs to a separate immutable result. The owner/source/cadence
and recurrence boundaries remain in the existing `ExportController` and
`dispatch` path. Optional backend construction is registered explicitly.

## Review and source checks

Independent review found two backend defects before physical work: CPU autocast
could silently switch output precision, and conversion exposed mutable backend
metadata. Both were corrected. Regression coverage exercises FP16/BF16 refusal,
owned metadata, version/source/weight/context rejection, exact sequential
reference outputs and resets, actor/source takeover, cancellation, RNG
preservation and a standalone process without learner imports.

Harness review also strengthened real-owner consumption checks, complete partial
exchange preservation, metered graceful closure and final budget/source/input
failure handling. Timing tests reject the historical 79-second count-only shape,
missing/reordered actor configurations and budget overruns. Synthetic failure
cases prove that refused, mixed, incomplete or early-revoked decisions cannot
enter a successful measured window. These fixtures are engineering conformance,
not measured game qualification.

An offline receipt compatibility check accepted the recorded per-tick action
and lifetime fields in all 160 retained trajectory decisions, including the
normal final-tick revocation. The archived step records omit three response
headers which that check supplied synthetically: trace completeness, dropped
idle trace count and unconsumed terminal commands. This is not retrospective
proof of those original response flags. The new capture records and requires
the actual fields for every measured decision.

After incorporating accepted main `cf01664d`, the full export-focused suite
completed 57 checks in 14.023 seconds: 53 passed and the four actual-host checks
were skipped because no physical run was configured. Independent review had
also passed the 16 new backend/harness regressions before the final additional
realtime-bound regression. Strict documentation validation checked 53 files
with zero errors or warnings, and `git diff --check` passed. These checks made
no host request and performed no optimizer update.
